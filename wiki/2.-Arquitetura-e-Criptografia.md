# 🔐 2. Arquitetura e Criptografia

O Concord foi construído sob o princípio fundamental de **Local-First Software**: sua máquina é a fonte primária de verdade, todas as operações são assinadas digitalmente e você nunca depende da disponibilidade de uma empresa ou nuvem para acessar suas informações.

---

## 🏛️ Separação de Processos e Sandbox (Electron)

Para garantir segurança rigorosa contra ataques de injeção ou falhas em dependências de terceiros, o cliente Desktop implementa uma separação rígida de processos com sandbox ativado:

```
┌───────────────────────────────────────────────────────────────┐
│               Electron: PROCESSO PRINCIPAL (Node.js)          │
│               • Privilegiado e isolado                        │
│               • packages/core (identidade, SQLite, Hyperswarm)│
│               • apps/desktop/src/main/ (janela, tray, updater)│
└───────────────────────────────┬───────────────────────────────┘
                                │ 
                                │ IPC (Barramento único tipado e validado)
                                │ Context Isolation + Sandbox ativados
                                ▼
┌───────────────────────────────────────────────────────────────┐
│              Electron: PROCESSO RENDERER (Chromium)           │
│              • Totalmente sem acesso direto a APIs Node.js    │
│              • apps/web (React 19, Tailwind, WebRTC)          │
│              • Preload script estrito (apenas expõe funções)  │
└───────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────┐
│                  JANELA DO OVERLAY IN-GAME                    │
│                  • Transparente, renderizada sobre jogos      │
│                  • Apenas exibe status e bolhas de voz        │
└───────────────────────────────────────────────────────────────┘
```

### Regras de Segurança dos Processos
1. **Sem `nodeIntegration`**: A interface gráfica (Renderer) não possui acesso a `fs`, `net`, `child_process` ou qualquer biblioteca de baixo nível do sistema operacional.
2. **Context Isolation**: O script de pré-carregamento (`preload/index.ts`) roda em um contexto de execução isolado e expõe apenas uma API limpa (`window.concord`) contendo métodos explícitos.
3. **Validação Rígida no IPC**: Qualquer chamada que cruze a barreira do IPC (`apps/desktop/src/main/ipc.ts`) é desestruturada e validada por esquema antes de tocar qualquer rotina do banco de dados ou da rede P2P.

## 🛡️ Camadas Criptográficas

A segurança das comunicações no Concord é composta por uma cadeia de protocolos criptográficos complementares:

| Camada | Tecnologia / Algoritmo | Propósito |
|---|---|---|
| **Identidade do Usuário** | Ed25519 (`node:crypto`) | Assinatura digital de operações, autenticação de sessões e geração de impressões digitais (`#abcd`). |
| **Proteção da Chave Local** | scrypt ($N=65536$) + AES-256-GCM | Cifragem do keystore no disco rígido usando a senha mestre local. |
| **Cifragem de Transporte P2P** | Protocolo Noise (via Hyperswarm) | Estabelece canais P2P cifrados entre nós da rede contra espionagem por ISPs ou intermediários. |
| **Autenticação de Conexão** | Desafio-Resposta (`auth:challenge`) | Impede que nós maliciosos na DHT declarem identidades falsas de outros usuários. |
| **Cifragem por Servidor** | AES-256-GCM (Chave de 256 bits) | Cada servidor possui sua própria chave simétrica. Apenas quem possui o convite consegue decifrar mensagens, nomes de canais e sinalização de voz. |
| **Áudio, Vídeo e Tela** | DTLS-SRTP (WebRTC nativo) | Criptografia em tempo real para pacotes UDP de mídia direta entre peers. |
| **Cifragem em Repouso (Vault)** | AES-256-GCM | Sela o conteúdo textual das mensagens e chaves de servidores pendentes antes da gravação no SQLite local. |

## 🔒 Criptografia em Trânsito: Detalhamento Técnico

### 1. Desafio de Autenticação (`auth:challenge` / `auth:proof`)
Quando dois nós se conectam via DHT do Hyperswarm, uma conexão TCP cifrada pelo protocolo Noise é estabelecida. No entanto, como a chave do Noise é efêmera, um nó poderia alegar pertencer a qualquer usuário.
- Para solucionar isso, assim que o canal abre, o nó receptor envia um desafio aleatório de 32 bytes (`auth:challenge`).
- O nó emissor assina esse desafio com sua chave privada Ed25519 e devolve a prova (`auth:proof`).
- Apenas se a assinatura for matematicamente válida a identidade é confirmada e registrada na tabela de conexões ativas (`p2p/node.ts`).

### 2. Chave Simétrica do Servidor (`serverKey`)
Diferente de sistemas convencionais onde servidores possuem um "banco central", no Concord um servidor é definido por um par criptográfico:
- **Tópico da DHT**: Um hash derivado da chave do servidor, usado para descobrir outros membros na rede sem revelar a chave de decifragem.
- **Chave de Cifragem (32 bytes)**: Uma chave secreta que viaja dentro do **Código de Convite**. Toda mensagem de chat, lista de canais e sinais de áudio transmitidos no escopo daquele servidor são cifrados com AES-256-GCM sob essa chave. Mesmo que um observador capture pacotes na DHT, ele só verá dados cifrados indecifráveis.

## 💾 Criptografia em Repouso: O Vault

O Concord armazena os dados locais em um banco de dados SQLite (`concord.db`) através do módulo `packages/core/src/crypto/vault.ts`.

### O que o Vault protege:
- **Conteúdo das Mensagens (`message.content`)**: Todo texto enviado ou recebido é cifrado antes de ser persistido na tabela do banco. Se alguém copiar o arquivo `.db` do seu computador, encontrará apenas blocos criptografados sem qualquer texto legível.
- **Chaves de Servidores em Convites Pendentes**: Os códigos de convite salvos no banco local também são selados para evitar o vazamento de credenciais de servidores aos quais você foi convidado.

> [!NOTE]
> Metadados como a lista de IDs de canais, nomes de servidores e cabeçalhos de operações do log permanecem indexáveis para garantir alta performance e buscas instantâneas na interface gráfica, enquanto os conteúdos confidenciais são protegidos pelo Vault.

## 🆔 Identificadores Autocertificados (Self-Certifying IDs)

Para impedir ataques onde um invasor tenta forjar o ID de um canal ou sequestrar um servidor existente (`server.create`), o Concord adota **Self-Certifying Identifiers**:

$$\text{ID} = \text{SHA-256}(\text{ChavePúblicaDoAutor} + \text{Nonce})$$

Quando um nó recebe uma operação de criação de servidor ou canal, o reducer calcula o hash e verifica se o autor assinou a operação. É matematicamente impossível para outro usuário registrar uma operação fingindo ter criado aquele ID, garantindo integridade absoluta ao grafo de permissões.
