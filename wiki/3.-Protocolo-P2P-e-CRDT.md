# 🌐 3. Protocolo P2P e CRDT

Sem um servidor central como árbitro supremo, como dezenas de usuários em fusos horários diferentes, com conexões instáveis e ordens de chegada distintas conseguem enxergar exatamente as mesmas mensagens, canais e permissões?

A resposta do Concord combina **Hyperswarm DHT**, **Log de Operações Assinadas**, **Relógios Lógicos de Lamport** e **Estruturas CRDT (Conflict-free Replicated Data Types)**.

---

## 📡 Descoberta de Nós e NAT Traversal (Hyperswarm)

O Concord utiliza a biblioteca **Hyperswarm** (da equipe Holepunch/Keet), uma das implementações de DHT (Distributed Hash Table) mais testadas do mundo:

1. **Tópicos Criptográficos**: Para cada servidor que você participa, o Concord deriva um tópico hash público a partir da chave secreta do servidor.
2. **Anúncio e Busca**: Seu nó anuncia na DHT que está interessado naquele tópico e simultaneamente busca outros nós anunciando o mesmo tópico.
3. **Holepunching (NAT Traversal)**: A maioria das pessoas está atrás de roteadores residenciais (NAT) sem portas abertas no roteador. O Hyperswarm utiliza técnicas avançadas de UDP Holepunching e UPNP para furar o NAT e estabelecer conexões TCP diretas peer-to-peer sem precisar de configuração manual no roteador.
4. **Canais Diretos**: Para mensagens privadas e convites entre amigos, cada usuário possui um **Tópico Pessoal** (sua "caixa de entrada" P2P), permitindo contato direto mesmo que não compartilhem nenhum servidor.

## 📜 O Log de Operações Imutável

No Concord, o estado do aplicativo (quais canais existem, quem são os membros, quais mensagens foram enviadas) não é sincronizado enviando o estado final do banco de dados. Em vez disso, o estado é modelado como um **Event-Sourced Replicated Log**:

$$\text{Estado Final} = \text{Reducer}(\text{Estado Inicial}, [\text{Op}_1, \text{Op}_2, \dots, \text{Op}_n])$$

### Formato de uma Operação (`ops/types.ts`)
Cada ação no sistema é representada por uma operação atômica:
```typescript
interface Operation {
  author: string;      // Chave pública Ed25519 do criador (hex)
  lamport: number;     // Timestamp lógico de Lamport
  seq: number;         // Número sequencial monótono do próprio autor
  type: string;        // Ex: 'message.create', 'channel.create', 'member.role'
  payload: unknown;    // Dados da operação (validados por schema)
  sig: string;         // Assinatura digital Ed25519 cobrindo todos os campos
}
```

### Serialização Canônica (`ops/canonical.ts`)
Em JavaScript, a ordem das chaves em um objeto `JSON.stringify()` não é determinística entre diferentes versões ou ambientes. Se Alice serializar `{ a: 1, b: 2 }` e Bob serializar `{ b: 2, a: 1 }`, os bytes mudariam e a verificação da assinatura criptográfica falharia.
O Concord implementa um serializador canônico rigoroso que ordena recursivamente todas as chaves em ordem alfabética antes de gerar ou verificar qualquer assinatura digital.

## ⏱️ Relógios de Lamport e Ordem Total Determinística

Em uma rede P2P real, relógios de relógio de parede (`Date.now()`) nunca estão perfeitamente sincronizados e podem ser facilmente fraudados por máquinas descalibradas ou maliciosas.

Para resolver a causalidade dos eventos, o Concord implementa **Relógios Lógicos de Lamport**:
1. Cada nó mantém um contador `lamport = 0`.
2. Ao emitir uma nova operação, o nó faz:
   $$\text{lamport}_{\text{nova}} = \max(\text{lamport}_{\text{local}}, \text{lamport}_{\text{maior\_recebido}}) + 1$$
3. Ao receber uma operação de outro peer, o nó atualiza seu relógio local:
   $$\text{lamport}_{\text{local}} = \max(\text{lamport}_{\text{local}}, \text{lamport}_{\text{recebida}})$$

### Ordem Total e Desempate
Quando dois nós criam operações no mesmo instante, como todos decidem qual veio primeiro?
O Concord estabelece uma **ordem total estrita e determinística**:
1. Compara pelo timestamp lógico `lamport` (menor valor vem primeiro).
2. Se houver empate no Lamport, compara pela **chave pública do autor** em ordem lexicográfica hexadecimal.
3. Se o mesmo autor tiver duas operações empatadas, compara pelo número de sequência local `seq`.

Graças a esse critério, mesmo que o Peer A receba as operações na ordem $(X, Y)$ e o Peer B as receba na ordem $(Y, X)$, ambos as ordenam exatamente da mesma forma antes de passar para o Reducer. O resultado final converge para um estado **100% idêntico** em todas as máquinas.

## 🔄 Sincronização Delta e Resiliência Offline

E se você desligar o computador por uma semana enquanto seus amigos continuam conversando?

1. **Heads de Replicação**: O Concord mantém em seu SQLite local um mapa dos "Heads": para cada autor conhecido, registra qual foi o maior `seq` já recebido e validado.
2. **Handshake de Sync (`sync:heads`)**: Quando você liga o computador e se reconecta a um peer no servidor, ambos trocam instantaneamente seus vetores de Heads.
3. **Envio Apenas do Delta**: Se seu peer notar que possui operações do autor Alice com `seq > 42`, enquanto você só tem até o `seq = 42`, ele empacota e envia **apenas o delta** (as operações faltantes).
4. **Idempotência**: Todas as operações do Reducer são idempotentes. Se por qualquer motivo uma operação repetida for entregue pela rede, o banco de dados a ignora silenciosamente sem duplicar mensagens ou corromper contadores.

## ⚖️ Operação Persistente vs. Dado Efêmero

Uma decisão de design crucial no Concord é saber **o que deve e o que NÃO deve ir para o log**:

| Categoria | Dado | Destino | Motivo |
|---|---|---|---|
| **Operação Assinada (CRDT)** | Mensagens de texto, canais criados, convites, cargos de moderação, nomes de perfil | Log SQLite replicado para sempre | Precisam sobreviver offline, replicar e compor o histórico imutável. |
| **Dado Efêmero** | Status online/ausente, digitação ("fulano está digitando"), sinais de voz/vídeo WebRTC | Socket temporário da conexão | Salvar esses dados no log geraria gigabytes de lixo permanente em poucos dias. |

Se um nó desconecta, os dados efêmeros somem imediatamente da memória; enquanto todo o histórico de operações permanece são e protegido no disco.
