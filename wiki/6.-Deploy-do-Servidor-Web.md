# 🚀 6. Deploy da Ponte Web (`apps/server`)

O Concord foi projetado primariamente como um aplicativo Desktop Electron. No entanto, para permitir que qualquer pessoa acesse o aplicativo pelo navegador de qualquer dispositivo (Windows, Mac, Linux, celular ou tablet) sem instalar nada, desenvolvemos a **Ponte Web (`apps/server`)**.

---

## 🏗️ Como Funciona a Ponte Web?

Em vez do processo Renderer falar com o processo Main via IPC do Electron, o navegador fala por **WebSocket** com a aplicação Node.js do `apps/server`:

```
┌─────────────────────────────────┐
│     Navegador (apps/web)        │
│   • React 19, Tailwind, WebRTC  │
│   • lib/webAdapter.ts           │
└────────────────┬────────────────┘
                 │ WebSocket persistente + HTTP estático
                 ▼
┌─────────────────────────────────┐
│      Ponte (apps/server)        │
│   • Express + ws                │
│   • Uma pasta por dispositivo   │
│   • Rate limiting & Proteções   │
│   • Usa diretamente @concord/core│
└────────────────┬────────────────┘
                 │
                 ▼
      Rede P2P (Hyperswarm DHT)
```

O código da interface gráfica não sabe e não se importa se está rodando no Electron ou no navegador: o módulo `webAdapter.ts` injeta um objeto `window.concord` com os mesmos métodos do Electron!

---

## 🔒 Arquitetura de Dispositivos e Isolamento

- **Uma pasta por dispositivo**: O navegador gera um token criptográfico aleatório único na primeira visita e o armazena no `localStorage`. Ao conectar, ele apresenta esse token (`session:hello`). O servidor calcula $\text{SHA-256}(\text{token})$ e aloca uma pasta isolada em `DATA_DIR/devices/<hash>`.
- **Persistência no F5**: Ao recarregar a página, o navegador apresenta o mesmo token e reabre o mesmo banco de dados local. A chave privada permanece cifrada pelo keystore e só é destrancada quando o usuário digita sua senha.
- **Uma aba ativa por vez**: Abrir uma segunda aba no mesmo navegador fecha a primeira (com código de encerramento WebSocket 4001), evitando que duas abas tentem travar o mesmo arquivo SQLite simultaneamente.
- **Faxina Automática de Lixo**: Pastas temporárias criadas por visitantes que nunca chegaram a criar uma conta são excluídas automaticamente ao desconectar, na inicialização e a cada 1 hora.

## 🐳 Opção 1: Deploy com Docker (Recomendado)

O repositório já inclui um `Dockerfile` pronto para produção com Node 22 e compilação de módulos nativos.

### Execução Simples:
```bash
# 1. Construir a imagem Docker
docker build -t concord-server .

# 2. Executar com volume persistente montado em /data
docker run -d \
  --name concord \
  -p 3001:3001 \
  -v concord_data:/data \
  -e NODE_ENV=production \
  -e TRUST_PROXY=1 \
  concord-server
```

## ☁️ Opção 2: Deploy em Plataformas de Nuvem (Railway / Render / Coolify)

### Railway
1. Acesse [railway.app](https://railway.app) e crie um novo projeto a partir do seu repositório no GitHub.
2. O Railway detectará o `Dockerfile` automaticamente.
3. Configure as variáveis de ambiente:
   - `NODE_ENV=production`
   - `PORT=3001`
   - `TRUST_PROXY=1` (essencial para que o rate limiting leia o IP real do usuário através do proxy do Railway).
4. Em **Volumes**, adicione um disco persistente montado no caminho `/data`.

### Render
1. Crie um novo **Web Service** conectado ao seu repositório.
2. Defina o Runtime como **Docker** e a porta como `3001`.
3. Adicione as variáveis:
   - `NODE_ENV=production`
   - `DATA_DIR=/data`
   - `TRUST_PROXY=1`
4. Em **Disks**, adicione um disco montado em `/data`.

## 🛡️ Configuração de Proxy Reverso (Nginx / Caddy)

Se você hospeda o Concord em uma VPS própria, utilize um proxy reverso para terminação TLS (HTTPS/WSS):

### Exemplo com Caddyfile (SSL Automático)
```caddy
concord.seudominio.com {
    reverse_proxy localhost:3001
}
```

### Exemplo com Nginx
```nginx
server {
    listen 443 ssl http2;
    server_name concord.seudominio.com;

    ssl_certificate /etc/letsencrypt/live/concord.seudominio.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/concord.seudominio.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## ⚙️ Tabela de Variáveis de Ambiente

| Variável | Valor Padrão | Descrição |
|---|---|---|
| `PORT` | `3001` | Porta HTTP e WebSocket na qual o servidor escuta. |
| `DATA_DIR` | `~/.concord-server` | Diretório onde os bancos de dados dos dispositivos são persistidos. |
| `NODE_ENV` | `development` | Se definido como `production`, ativa verificação e redirecionamento HTTPS. |
| `TRUST_PROXY` | `0` (desligado) | Defina como `1` quando estiver atrás de Cloudflare, Nginx, Caddy, Railway ou Render. |
| `ALLOWED_ORIGINS` | *(vazio)* | Lista separada por vírgulas de origens adicionais autorizadas a conectar no WebSocket. |
| `MAX_SESSIONS` | `50` | Limite máximo de sessões ativas simultâneas no processo. |
| `MAX_SESSIONS_PER_IP` | `3` | Limite de sessões simultâneas permitidas a partir de um mesmo IP. |
| `MAX_PAYLOAD_BYTES` | `262144` (256 KB) | Tamanho máximo aceito por mensagem WebSocket. |
| `CALLS_PER_WINDOW` | `60` | Quantidade máxima de chamadas IPC permitidas por janela de tempo. |
| `CALL_WINDOW_MS` | `1000` (1 seg) | Tamanho da janela de medição de chamadas por segundo. |
| `MAX_UNLOCK_FAILURES` | `5` | Quantidade de tentativas de senha incorreta antes de aplicar bloqueio temporário. |
| `UNLOCK_LOCKOUT_MS` | `60000` (1 min) | Duração do bloqueio temporário em caso de força bruta de senha. |
